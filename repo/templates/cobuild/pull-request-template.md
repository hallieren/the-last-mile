## The Three Explain-It Questions (checked face to face or on video by the module's gatekeeper before merging; any question unanswered and it is sent back)

The rule in one sentence, **if you cannot say it, do not merge it.** Applies to both sides alike, your team's commits get checked the same way.

### 1. Why is it written this way?

(Every non-obvious choice, retry counts, timeout values, the algorithm, edge-case handling, you can state the reason and why you did not pick an alternative. "That is how the agent wrote it" does not count as a reason.)

____

### 2. Where can it go wrong, and how would you find out?

(The concrete failure path, who catches it, what the logs/alerts look like. "It should not go wrong" and "The tests all passed" do not count as answers.)

____

### 3. If it has to change, where do you start?

(The next foreseeable requirement change, where the change point is, how far it reaches.)

____

---

A rejection does not mean the code failed, it means the explanation failed. Before resubmitting, the submitter must actually have touched the code (rewriting, simplifying, adding tests all count). Reciting it back from memory does not.
